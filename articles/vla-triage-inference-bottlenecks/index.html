基本信息与来源

原文 Where Is VLA Inference Time Spent? Bottlenecks and Optimization Interactions Across GPUs，Muhammad Danish Waseem、Ahmed Ali-Eldin Hassan。首次提交 2026-11-04 16:09 UTC；读取 arXiv:2611.06710v1，版本日期为 2026-11-04；整理及实质修订日期为 2026-11-08。近期工程补读，非今日首发。已阅读正文、测量协议、关键附录及限制条件；数字为作者测量，未独立复现。

固定全文、PDF、版本记录提供原始依据。本次未核验到作者完整测量仓库或结果日志下载；引用 torchao、FlashInfer 等库不代表本文流水线已公开。它是测量与部署指南，不提出新的训练策略，也没有验证优化后的任务成功率。

一句话总结与研究问题

先在目标硬件上确定真正的模型执行模式与瓶颈，再测优化组合；剪枝、量化、编译和减少采样步数的独立加速比通常不能直接复用。

§2–3覆盖七种 VLA、H100/A10G/RTX4090/Jetson Thor 四类 GPU-host 平台和七类优化。不同架构的关键路径不同，CPU launch、权重带宽和核函数效率也会相互替代。主机 CPU 与软件栈不完全一致，因此跨平台差异不是纯 GPU 架构因果实验；文中没有 RTX4090 的量化结果，不能据此直接推荐用户的量化精度。

公式直觉：先更新阶段占比，再谈收益

若受影响阶段占总时延比例 σ，阶段加速 s 倍，则总节省为 g = σ(1−1/s)。前一次优化会改变 σ，也可能改变矩阵形状和核函数效率 s，因此后一优化的收益也会变。§5用四次测量 T0、T1、T2、T12 检验组合，而不是默认 T12 = T1×T2/T0，也不是把独立节省毫秒数直接相加。

对异步动作队列，名义预算为 B = A_remaining × Δt，真正留给模型的预算还要减去预处理、通信与抖动余量。§6强调选择执行模式之后重新测阶段占比，再检查剩余优化空间。这个预算回答队列是否耗尽，不回答旧观测是否已经不可用于接触反应；满足吞吐期限不等于闭环安全。

关键测量与对照

§3.1从 CPU 图像预处理后开始计时，至模型返回动作，常规配置至少 200 次推理、报告中位数，batch 对照为至少 100 批；并使用 CPU 绑核、预热及重复测量。因此这些值不是相机到驱动的完整端到端 P99。

§1、附录 C显示 OpenVLA-OFT/H100 的 FastV 50% 剪枝，相对 unfused attention 可省 21.4%，相对 FlashAttention-2 则只省 6.9%。需要读取 attention 权重的选择器可能迫使后端退回较慢实现；若基线不是部署后端，所谓加速会被高估。

§5.1给出 SmolVLA/RTX4090 的编译加减少采样步数案例：沿用 eager 百分比会估出 17.4ms，实测组合为 56.9ms。它是特定设置的交互反例，不是该模型所有配置的固定时延。文中的 token 剪枝主要用随机选择隔离 token 数的成本，因此没有证明如此剪枝还能完成任务。

§6另以 CogACT/A10G 说明，某编译、剪枝、int8 组合为 49.6ms，虽然低于名义 50ms，但预处理和余量扣除后仅剩 40.5ms，仍不满足部署预算。CUDA graphs 还需要固定形状及显存池，多 pruning level/batch 的图并存可能超出显存；编译准备时间也不属于稳态推理收益。

局限与复现要求

附录 H明示候选筛选与偏好顺序只是在已有测量网格上检查，不是精度排序。权重读取下界假设每次都从 DRAM 读取、至少四位且不改变层/前向次数，存在跨步缓存等条件时要重新论证。文中的 5.3% 筛选余量来自测量稳定性经验，不是任意系统的抖动上界。

剪枝、量化、减步都需要新任务评测；即使图和编译保持预期计算，也要检查数值误差、mask 和缓存。预处理、网络、ROS 调度、控制跟踪、传感延迟及热降频未由模型中位数覆盖，不能据此声称真机达到某个 Hz。

迁移实验：给现有 RTC 建立四测量矩阵

以下为分析建议。对现有 X5 30Hz、RTC H=30、D=5–6、blend=4，先保持采样步数、动作坐标、触发阈值和检查点一致，记录预处理、H2D、视觉、prefill、动作生成、D2H、通信和队列接入各阶段。驱动发布周期与策略重规划周期分别报告，不能把 30Hz 发布当作每秒 30 次新观测决策。

在同一端侧硬件、功率、软件和相机输入上比较 eager、graph、compile，锁定部署模式后再作单优化及双优化四格对照。使用同一批离线观测、相同噪声种子并校验输出，常规至少数百次预热后测量；日志包含中位数、P95/P99、图重新捕获、显存峰值和队列耗尽。候选筛选器的同步或后端退化也要计时，不能仅测删除 token 后的 Transformer。

若队列剩余 10 步，30Hz 下名义窗口约 333ms；这是预算演算建议，不是观测年龄上限。留出实测通信与调度尾延迟后，再决定是否调整触发点。优化后复测成功率、接触失败、夹爪切换、边界 jerk 与总任务耗时；先用仿真或低速空载验证，保持急停及关节/速度限制。不要同时改 RTC 参数和量化精度后把所有收益归给其中一个模块。

精读路线与面试追问

优先读 §3.1 的计时边界、§5 的四时延比较、§6 的预算及附录 B/H。实现可用后先核对真实后端、编译范围、缓存形状、GPU 同步和显存池，而不是先运行一个通用量化命令。

面试可问：算力更强的 GPU 为什么某项优化反而更慢？为什么少 token 不一定快？如何证明自己测到的是推理而不是异步 launch？RTC 无停顿为何仍可能反应迟钝？答案要区分算力、带宽、launch、后端和闭环时序，不只报 FLOPs。
